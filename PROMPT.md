# Спецификация доработок платформы

Формат для каждого раздела: **Результат** (что должно получиться) → **Что чинить** (текущая проблема) → **Как делать** (подход) → **Ключевые ошибки** (на что обратить внимание, чтобы не сломать по-новому).

Там, где стоит `[...]` — впиши свою конкретику (шаги воспроизведения бага, названия файлов/роутов). Без этого агент будет угадывать.

---

## 1. Роли и доступ (/account, /admin)

**Результат:**
Пользователь при заходе на `/account` видит интерфейс, соответствующий своей роли (student → кабинет ученика, teacher → кабинет учителя). `/admin` доступен только роли admin, остальные получают редирект/403.

**Что чинить:**
`[опиши: сейчас путается роль? teacher видит student-интерфейс? admin доступен всем?]`

**Как делать:**
- Роль должна проверяться на backend (middleware/guard), а не только на фронте — иначе смена роли в devtools открывает чужой кабинет
- Один источник правды для роли (JWT payload или сессия в БД), фронт не должен сам решать, что показывать

**Ключевые ошибки:**
- Проверка роли только в UI (можно обойти через URL)
- Рассинхрон роли между токеном и БД после смены роли пользователем

## 2. Backend-связь и отображение учеников

**Результат:**
Список учеников у учителя/админа загружается корректно, без пропусков и дублей, актуальный после любых изменений (добавление/удаление).

**Что чинить:**
`[опиши: список не обновляется? часть учеников не приходит? ошибка запроса?]`

**Как делать:**
- Проверить, что эндпоинт отдаёт полный список с пагинацией/фильтром, а фронт не кэширует устаревшие данные (invalidate query после мутаций, если TanStack Query/аналог)
- Свериться, что связь teacher↔student в БД (какая таблица/foreign key) действительно отражает реальные назначения

**Ключевые ошибки:**
- Устаревший кэш на фронте после создания/удаления связи ученик-учитель
- N+1 запросы при росте числа учеников (влияет и на пункт про скорость)

## 3. Корректное создание заданий

**Результат:**
Учитель создаёт задание любого типа (см. список с скриншота: один вариант, несколько вариантов, пропуски, сопоставление, лексика, грамматика, чтение, аудирование, письмо, говорение) — и оно сохраняется и отображается именно с тем типом и структурой, который выбран.

**Что чинить:**
`[опиши конкретный баг: например — выбираешь "Сопоставление", а сохраняется как "Один вариант ответа"?]`

**Как делать:**
- Проверить маппинг: значение из dropdown → enum/тип в БД → компонент рендера на фронте. Разрыв обычно в одном из этих трёх мест
- Один тип задания = одна чёткая схема данных (какие поля обязательны для "Сопоставление" vs "Письмо" — это разные структуры)

**Ключевые ошибки:**
- Тип задания и его данные хранятся отдельно и могут разъехаться
- Фронт рендерит по дефолтному типу, если тип не распознан (маскирует баг)

## 4. Управление учителями + студентами (админ)

**Результат:**
Админ может просматривать, добавлять, редактировать, деактивировать учителей и студентов из одной панели.

**Что чинить:**
`[опиши: чего не хватает — самого функционала, прав, или UI?]`

**Как делать:**
- Отдельные admin-only роуты с явной проверкой роли на backend
- CRUD с подтверждением необратимых действий (удаление/деактивация)

**Ключевые ошибки:**
- Отсутствие проверки роли на backend для admin-роутов (см. пункт 1)
- Жёсткое удаление вместо деактивации — теряется история

## 5. Скорость сайта

**Результат:**
`[опиши целевое ощущение: конкретные страницы, которые тормозят, и насколько]`

**Как делать:**
- Сначала измерить (Lighthouse / network tab), а не чинить вслепую — иначе оптимизируешь не то место
- Частые причины: N+1 запросы к БД, отсутствие индексов, не оптимизированные изображения, лишние ре-рендеры на фронте

**Ключевые ошибки:**
- Оптимизация без замера "до/после" — не поймёшь, помогло или нет

## 6. Cambridge-логика создания заданий + "Говорение"

**Результат:**
Каждый тип задания из списка соответствует Cambridge-формату (форматы вопросов, критерии оценки), включая "Говорение" — с учётом того, что это устный ответ, а не текст/выбор.

**Что чинить:**
`[опиши: "Говорение" вообще не реализовано? или реализовано неправильно?]`

**Как делать:**
- Определить для "Говорение": как ученик отвечает (аудиозапись? речь→текст?), как это проверяется (вручную учителем? AI-оценка произношения/беглости?)
- Свериться со стандартом Cambridge для соответствующего уровня (что именно оценивается: fluency, grammar range, pronunciation и т.д.)

**Ключевые ошибки:**
- Смешение логики письменных и устных заданий в одном компоненте — из-за этого чаще всего и «съезжают» типы (пункт 3)

---

## 7. Проверка домашней работы

**Результат:**
Каждый тип задания проверяется соответствующим способом:
- Один/Несколько вариантов, Заполнить пропуски, Сопоставление → автоматическая проверка по ключу
- Лексика/Грамматика/Чтение/Аудирование → авто или частично авто
- Письмо/Говорение → ручная проверка учителем или AI-оценка по критериям

**Что чинить:**
`[опиши: сейчас проверка вообще не различает типы? падает на каких-то типах? неверный балл?]`

**Как делать:**
- Один диспетчер проверки, который по типу задания вызывает свою функцию оценки — не одна универсальная функция "на все типы"
- Для Письмо/Говорение — четко решить: живой учитель или LLM-агент с рубрикой (и что происходит, если LLM не уверен)

**Ключевые ошибки:**
- Одна общая функция проверки для всех типов (источник большинства багов из пункта 3 и 6)
- Нет чёткого fallback, если авто-проверка не может оценить (например Говорение без транскрипции)

## Как использовать этот файл с агентом

1. Заполни `[...]` для 1-2 разделов, которые сейчас важнее всего (советую начать с №3 и №7 — они связаны между собой)
2. Отдавай агенту **один раздел за раз**, не весь файл целиком
3. После правки — прогони "Как проверить" сценарий из раздела, прежде чем переходить к следующему
